# Pre-QA smoke gate (oho-web-app)

Use this when a change is proposed for QA. The feature worktree is the **candidate**; `Create-image-reflec-for-QA` is a tooling worktree, not the version of the app under test. ClickUp owns task status. Orca/OMP (retired 2026-10): see archive/2026-10-orca-omp/context/oho-web-app/QA.md This folder holds evidence and handoff pointers, not another task queue.

1. In the candidate worktree, identify the branch and exact HEAD, the changed user flow, expected result, affected roles, and the API/environment needed. Identify focused tests from the change; run them there. A test pass is supporting evidence, not the smoke result.
2. Run the candidate app against a safe, identified environment. Exercise the **changed behavior** end-to-end (browser for UI work), including an observable success result and the relevant permission or failure path. Use a restricted account when the change affects visibility/permissions; for owner-only flows, verify owner and business identity. Do not substitute a static fixture or an unrelated login-page check for a real feature smoke. Capture non-sensitive evidence (test log, screenshot, request/response summary) without credentials or customer data.

   - For screenshot-led UI issues, use the screenshot as a checklist: enumerate each reported element and interaction (including hover states), identify its owning component, and trace the actual data path from API request/response through adapter/feature flag, store/page state, props/computed values, and rendered UI.
   - In the browser smoke, verify both initial-load data and mutation/save response propagation, plus relevant platform identifiers and alternate API/feature-flag paths. Directly injecting final component props or using only a static fixture does not prove this flow.
3. For code-first refactors, the tooling worktree has `npm run qa:refactor -- --config=<scope-config>`; create the config from the changed code and approved expected behavior, use `PLAYWRIGHT_BASE_URL` for the candidate app and an owner storage state with `TEST_BUSINESS_ID`. Inspect the generated `manifest.json`: every required surface, owner/business check, request/state/UI check must pass. See the tooling worktree's `e2e/README.md` for the runner contract. This capture is an optional supplement, not a substitute for step 2.
4. Write `.ai/handoffs/<work-item>.md` with the candidate repo/worktree, branch and HEAD, linked issue/spec, tested role/environment, smoke steps and observed outcome, focused-test result, evidence paths, unresolved risks, and verdict **Ready for QA** or **Blocked**. Link to the source repo and local artifacts rather than copying secrets or large outputs into `.ai`.

   Shared handoffs must link branch-local evidence explicitly to the recorded candidate (for local files, an absolute `file:///...` URI). Relative links are only for other shared-context documents. Open each evidence link before handing off; a missing candidate/artifact is a blocker, not permission to resolve it against the current checkout.

**Gate:** Ready for QA requires a passing, task-specific smoke of the candidate revision plus recorded evidence and any required focused checks. A failed check, missing safe runtime/auth, changed HEAD after the smoke, or missing proof means Blocked. Do not send a blocked change to QA or interpret a passing synthetic runner fixture as release evidence. QA receives the handoff link; this process does not commit, merge, deploy, or change a ClickUp task status automatically.
