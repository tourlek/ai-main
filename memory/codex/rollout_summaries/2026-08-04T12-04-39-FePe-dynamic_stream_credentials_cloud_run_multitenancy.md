# Dynamic Stream Chat credentials for multi-account OHO

Rollout context: The user asked what tool to use for dynamic environment configuration, then clarified that Stream Chat credentials are secrets and must be separated by `business_id`.

## Task 1: Choose a dynamic configuration mechanism

Outcome: success

Key steps:
- Distinguished feature flags, runtime configuration, secrets, and environment-specific infrastructure values.
- Recommended Firebase Remote Config only for non-secret flags/configuration.
- Identified Cloud Run environment variables as revision-bound rather than truly runtime-dynamic; changes create a new revision.
- Recommended Secret Manager for credentials and a database mapping for selecting them by business.

Reusable knowledge:
- OHO browser Firebase Remote Config must not become authoritative for per-business credentials or flags because SDK storage can be shared across tabs; backend bootstrap should remain authoritative where applicable.

## Task 2: Secure multi-account Stream Chat credential selection

Outcome: success

Preference signals:
- When the user clarified “มันเป็น secreat เลยเพราะต้องทำ multi account streamchat แยกตาม business” -> treat Stream `api_secret` as server-only and design around per-business credential resolution rather than exposing or dynamically injecting secrets into the frontend.

Key steps:
- Proposed MongoDB mapping keyed by `business_id`, storing Stream API key plus Secret Manager resource and pinned secret version; the actual `api_secret` remains in Secret Manager.
- Backend resolves `business_id` from the authenticated session, loads the corresponding secret, creates a Stream server client, generates an expiring user token, and returns only the API key and user token to the frontend.
- Recommended caching clients by connection identifier and secret version with TTL/LRU, while avoiding one global Stream singleton.
- Recommended secret rotation by adding a new Secret Manager version and updating the mapping, rather than relying on `latest`, to preserve rollback clarity.
- Mentioned Stream Teams as an alternative if businesses can share one Stream app/account and only need tenant isolation.

## Task 3: Whether Cloud Run must be duplicated

Outcome: uncertain

Key steps:
- Answered that one Cloud Run service can serve multiple Stream accounts. Each request resolves the authenticated business, looks up its mapping, accesses the correct secret, and selects a cached per-account client.
- Clarified that separate Cloud Run services are only justified for infrastructure/compliance isolation such as distinct service accounts, networking, scaling, deployment, or strict operational boundaries.

Failures and how to do differently:
- Do not store per-business Stream secrets in Firebase Remote Config, frontend runtime config, or a single global Cloud Run environment variable.
- Do not trust an arbitrary `business_id` from the request body without authorization checks.
- Do not use a global Stream client across businesses; cache clients using a business/connection and secret-version-aware key.
